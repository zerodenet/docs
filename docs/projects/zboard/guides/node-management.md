# 节点与协议服务管理

Zboard 将基础设施节点、协议服务和商业订阅分离管理。节点描述可运维的服务器，协议服务描述对外提供的网络能力，节点组和订阅模板决定用户最终获得什么。

## 资源关系

```text
供应商账号 / VPS 节点资产
              ↓
      Zero 安装与运行状态
              ↓
        Protocol Service
              ↓
           Node Group
              ↓
      Subscription Delivery
```

DNS 记录和托管证书关联到节点与协议服务，但仍是独立资产。

## 节点接入

节点接入通常包含：

1. 配置 VPS 基础信息和 SSH 凭证；
2. 验证 SSH 连接和主机身份；
3. 安装或关联指定版本的 Zero；
4. 启动仅供接入使用的 loopback bootstrap 控制入口；
5. 检查 Zero 控制面和 Connector；
6. 创建协议服务；
7. 发布配置并检查运行状态和事件上报。

节点在尚未拥有公开协议入站时，也需要能够稳定完成 Zero onboarding。当前版本会使用 loopback-only bootstrap inbound 保持控制面和 Connector 可用，不再要求为了“让 Zero 先活着”临时发布一个对外服务。

## Zero 健康与 Connector 在线是两个状态

不要把 Connector 最近有事件等同于 Zero 数据面健康，也不要因为 Zero 进程存在就推断 Connector 正常。

- **Zero 健康**：描述内核控制面、活动配置和数据面运行状态；
- **Connector 在线**：描述 Zboard 最近是否持续收到该节点的 Connector 事件。

两者需要分别判断。节点详情和 Dashboard 会按各自事实展示状态；发布流程也不应使用 Connector 存活替代 Zero 激活验证。

节点显示“在线”只能证明对应的连接或上报事实。协议服务是否可用还取决于配置验证、端口监听、证书、实际内核能力和最近一次发布结果。

## Zero 版本选择

节点可以选择明确的 Zero 发行版本。选择时应区分正式版和预发布版，并按语义版本比较，不要按字符串排序。

批量协调内核版本时需要明确指定目标版本；降级必须显式允许，不应让一次普通 reconcile 隐式把已安装的新版本替换为旧版本。

不同协议能力有最低版本要求，例如 Trojan/Hysteria2 托管用户和 Mieru 用户归属。Zboard 会在创建或发布前检查所选节点版本；不满足要求时先升级节点，不应通过共享占位凭据绕过限制。

## 协议服务

协议服务负责描述：

- 协议和监听端口；
- TLS、REALITY 和传输方式；
- 客户端订阅模板；
- 托管证书；
- 流量倍率和运营名称；
- 所属节点及最近发布状态。

协议服务配置支持复用、审计和重新发布，但运行时仍绑定到具体节点。详细字段和版本边界见[协议服务配置](./protocol-services)。

当前运行配置可以为协议端点先建立监听器，再根据实际订阅用户投影凭据。没有用户凭据时，不应凭空生成共享身份；凭据归属仍以业务 principal 为边界。

## 发布流程

一次完整发布应完成：

1. 根据协议服务和订阅用户能力编译 Zero 配置；
2. 在目标节点运行配置校验；
3. 原子替换或激活配置；
4. 检查 Zero 控制面、活动配置和协议监听；
5. 独立确认 Connector 最近仍在上报；
6. 更新协议服务的实际发布状态。

任何一步失败都不应把未验证能力提前暴露给订阅。修复首个错误后重新发布，并保留失败任务和审计记录。

## 节点运行诊断

节点诊断只返回 **Zboard 负责的业务状态**，而不是把整台主机的日志、进程、连接表或资源细节全部暴露给后台。

诊断会围绕当前节点已分配的协议服务检查：

- SSH 是否可用；
- Zero 状态是否可读取；
- 该节点被 Zboard 管理的协议端点是否实际存在对应监听。

宿主机监听表可以作为诊断过程中的临时输入，但返回给管理端的是业务协议的健康/失败结果，不会把无关端口、进程、内核日志等作为“诊断详情”公开。

CPU、内存等 SSH 资源采样需要管理员显式触发。BBR 状态探测也不会在打开普通节点列表时隐式执行，避免后台浏览页面持续产生 SSH 命令。

## VPS 系统操作：BBR

对已完成 SSH 和主机身份验证的 Linux 节点，Zboard 可以显式检查 BBR 状态并提交“启用 BBR”系统操作。

该操作具有以下边界：

- 只有完成 SSH 验证的节点才能执行；
- 先检查内核是否提供 BBR；
- 通过持久化任务执行，而不是浏览器请求一直阻塞到 SSH 完成；
- 写入受 Zboard 管理的 sysctl 配置，并验证 `fq` 与 `bbr` 是否实际生效；
- 执行失败时保留任务错误和审计事实；
- 如果目标内核不支持 BBR，不应留下半完成的系统配置。

BBR 是管理员主动执行的 VPS 系统操作，不是节点上线的隐式前置条件。

## 删除节点

删除受管节点前，Zboard 会先让该节点上的受管 Zero 进入静默/停止状态，再继续清理节点相关业务资源。这样可以避免数据库关系已经删除，但旧 Zero 仍继续运行并向 Connector 上报的“幽灵节点”。

删除仍然是高影响操作。执行前应确认协议服务、节点组、DNS/证书和订阅引用的级联影响；删除后的远端运行状态不应仅靠数据库记录是否消失来判断。

## 节点组与运营配置

节点加入并发布协议服务后，可以进一步关联：

- 节点组；
- 套餐和 SKU；
- 订阅模板；
- 流量倍率和统计规则；
- DNS 记录与证书。

节点组引用协议服务，而不是直接引用一台裸服务器。这样可以在迁移服务或调整传输时保持上层商业配置稳定。

## 日常检查

- 节点 Zero 版本与期望版本一致；
- 最近发布状态成功；
- Zero 健康与 Connector 在线状态分别正常；
- 已分配协议服务的监听状态正常；
- SSH 资源或 BBR 只在需要时显式采样；
- DNS 记录指向正确节点；
- 证书在有效期内且绑定关系正确；
- 订阅预览包含预期节点和本地 Mixed 入口；
- 流量记录能够归属到订阅用户。

全局 Dashboard、系统时区和历史保留策略见[运营概览与系统设置](./operations)。Zero 的底层协议能力、配置模型和控制接口请参考 [Zero Core 项目仓库](https://github.com/zerodenet/core)。
