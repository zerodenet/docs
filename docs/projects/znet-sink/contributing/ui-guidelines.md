# 客户端 UI 规范与实现标准

::: warning 开发基线
本页按 ZNet Sink `develop@912d1dc` 的 Svelte/Tauri 客户端实现整理，用于新增页面、重构和代码评审。它描述客户端整体标准，也包含插件宿主页面的额外约束。
:::

ZNet Sink 是固定视口的桌面应用。页面结构应当像应用工作区，而不是随内容增长的网页文档。

## 1. 视口和滚动所有权

应用根节点固定为窗口大小并隐藏溢出：

```css
html,
body {
  width: 100%;
  height: 100%;
  overflow: hidden;
  overscroll-behavior: none;
}

.app-workspace {
  display: flex;
  flex: 1;
  min-width: 0;
  min-height: 0;
  overflow: hidden;
}

.content-scroll {
  flex: 1;
  min-width: 0;
  min-height: 0;
  overflow: auto;
  overscroll-behavior: contain;
}
```

每个工作区只指定一个主要滚动所有者。`flex: 1` 的祖先链必须逐层设置 `min-height: 0`，横向内容容器同时设置 `min-width: 0`。禁止通过给 `body`、根页面或整个卡片增加 `overflow: auto` 来修复局部溢出。

需要固定工具栏、页签或底栏时，只让中间内容区滚动。插件管理 iframe、代码编辑器、日志等拥有内部滚动时，外层内容区应使用 `overflow: hidden`，避免双滚动条和滚轮穿透。

## 2. 页面结构

专业模式页面遵循以下层次：

1. 页面或面板标题：名称、简短说明、一个主要动作；
2. 工具栏：视图切换、搜索、刷新和次要动作；
3. 内容区：卡片、列表、设置分组或详情工作区；
4. 当前操作反馈：靠近触发操作显示，不能被弹窗遮挡。

优先复用客户端已有组件和模式：

- `desk-card`：顶层面板；
- `SectionWorkspace.svelte`：左侧分组导航 + 右侧内容；
- `DraggableModal.svelte`：可拖动、可全屏的复杂弹窗；
- `AppSegmentedControl`：页面页签或卡片/列表视图切换；
- `Button`、`Input`、`Switch`、`Dialog`：标准控件和确认流程。

不要为单个页面复制一套边框、阴影、按钮或弹窗层级。

## 3. 视觉令牌

颜色和状态必须使用主题令牌，例如：

- `--background` / `--foreground`；
- `--card` / `--surface`；
- `--muted` / `--muted-foreground`；
- `--border` / `--input` / `--ring`；
- `--primary` / `--primary-foreground`；
- `--success` / `--warning` / `--destructive`。

新增组件不能写死只适合浅色主题的背景、文字或边框颜色。状态色用于表达状态；普通主按钮使用 `primary`，破坏性操作使用 `destructive`，成功和警告不要替代正文层级。

界面使用紧凑的桌面密度。相同层级的标题、说明、工具栏和输入控件应复用现有字号、间距和圆角，不在业务组件中发明新的视觉体系。

## 4. 文本和信息密度

名称、版本、插件 ID、来源和路径等不可控文本必须允许收缩：

```css
.identity {
  min-width: 0;
  overflow: hidden;
  text-overflow: ellipsis;
  white-space: nowrap;
}
```

被截断内容应通过 `title` 或等价悬浮提示展示全文。版本号不能被强制拆成多行。简介在卡片中最多显示约两行，在列表中显示一行；完整说明放到详情页。

普通用户界面不直接展示原始 JSON。技术详情可以放入折叠的诊断区，并同时提供面向用户的结论、原因和下一步操作。

## 5. 卡片与列表

管理型集合同时支持卡片和列表时，两种视图必须保持相同的信息和操作语义：

- 卡片适合浏览说明；列表适合高密度管理；
- 视图偏好可以本地保存；
- 整张卡片或整行作为进入详情的点击目标；
- 内部开关、菜单和链接阻止事件冒泡，仍可独立操作；
- 不再额外放置重复的“详情”按钮；
- 尾部状态、开关和动作形成一个紧凑操作区，不孤立悬浮在行尾。

交互元素必须使用 `button`、`a`、`input` 等语义元素，保留键盘焦点和明确的 `aria-label`。只有鼠标悬浮可见的操作必须仍能通过键盘获得。

## 6. 弹窗和层级

复杂弹窗使用 `DraggableModal`：标题和说明在固定 header，中间 body 填满剩余高度，可选 footer 固定在底部；全屏、关闭、Escape、焦点陷阱和焦点恢复由公共组件处理。

弹窗必须受当前窗口约束：

- 普通状态不超出 `100dvh`；
- 全屏状态填满窗口；
- 复杂工作区设置 `bodyScrollable={false}`，并在内部只定义一个滚动区；
- backdrop 自身不滚动，也不能让底层页面滚动。

一个业务流程只使用一个主弹窗。需要预检、权限确认或来源确认时，在当前弹窗内部切换步骤，不再打开同级或更高层弹窗遮住它。必须二次确认的破坏性操作可以使用标准确认 `Dialog`，但不能与另一个文件选择或安装弹窗竞争层级。

错误应显示在当前步骤内部并触发 Toast；成功后关闭流程并提供明确反馈。不要把错误写到被遮挡的页面底部。

## 7. 加载、禁用和反馈

- 首屏外壳渲染与运行时初始化分离，后台初始化不能阻塞页面点击；
- 加载状态使用局部 spinner、骨架或状态文本，并保留仍可安全执行的操作；
- 提交期间禁用会造成重复事务的按钮；
- 错误信息说明失败对象和下一步，不用“未知错误”覆盖后端的明确原因；
- 用户取消不是系统故障；
- 长时间下载展示来源、阶段、进度和重试状态；支持续传时明确说明同一制品会继续缓存进度。

## 8. 插件页面标准

插件管理页分成两个视觉所有者：

### 客户端外壳

客户端统一渲染：

- 已安装插件列表和卡片；
- 名称、版本、发布者、简介和 ID；
- 启用状态、权限、关于、更新和卸载；
- 安装市场、目录刷新、本地安装和信任确认；
- 下载、校验、兼容性和权限变化反馈。

已安装插件整行或整卡进入详情。详情外壳固定为“管理 / 权限 / 关于”；管理内容存在时应填满余下高度：

```css
.plugin-detail-scroll.management-active {
  overflow: hidden;
}

.plugin-management-surface {
  display: flex;
  flex: 1;
  min-width: 0;
  min-height: 0;
}
```

### 插件管理页面

插件自行渲染登录、配置、资源选择、同步、自检和帮助。页面必须适应宿主提供的宽高，不假定固定窗口尺寸；内容较少时仍铺满容器，内容较多时只在自己的主内容区滚动。

插件页面使用宿主注入的主题令牌，保持浅色和深色主题可读。页面不能覆盖客户端导航、启用开关、权限页或关于页，也不能模拟系统授权提示。

安装插件使用一个弹窗完成：市场列表默认安装最新兼容版本；刷新目录与“从本地安装”位于同一工具栏；本地包预检和发布者信任确认在弹窗内部切换。已经安装的插件才进入版本管理与更新流程。

## 9. 窄窗口和可访问性

客户端主要面向桌面窗口，但所有工作区都必须在窄窗口中保持可操作：

- 工具栏允许分组换行或转为纵向；
- 双列配置在窄窗口降为单列；
- 列表保留名称和主要操作，把说明移到下一行；
- 不通过缩小到不可读字号解决空间不足；
- 图标按钮提供 `title` 和 `aria-label`；
- 状态更新使用适当的 `role="status"`、`role="alert"` 或 `aria-live`；
- 模态打开后移动焦点，Tab 不离开弹窗，关闭后恢复原焦点。

## 10. 实现检查清单

提交 UI 变更前检查：

- [ ] 根页面没有出现浏览器式整体滚动；
- [ ] flex 链路设置了必要的 `min-width: 0` / `min-height: 0`；
- [ ] 每个工作区和弹窗只有一个主要滚动区；
- [ ] 浅色、深色、普通窗口、窄窗口和全屏均可操作；
- [ ] 加载、空状态、错误、禁用和成功反馈完整；
- [ ] 长文本省略且能查看全文；
- [ ] 卡片和列表的信息、状态与动作一致；
- [ ] 键盘可以到达所有操作，焦点样式清晰；
- [ ] 弹窗没有互相遮挡，反馈没有写到遮罩后面；
- [ ] 插件业务 UI 留在沙箱页面，权限和生命周期留在客户端外壳；
- [ ] UI 变更通过当前前端检查，并完成至少一次真实窗口交互验收。
